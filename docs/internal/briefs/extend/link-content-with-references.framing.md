## Background the page rests on

- **The model.** A `reference` field stores another entry's id in frontmatter, typed to the one concept its `concept` option names, and `fields.array(fields.reference(...))` stores a list (`f:563h9u`, `f:rfc0nc`). The edge's concept comes from the declaration, never the stored value, so the file holds the id alone (`f:9i99mg`). The link's text and address come from the target entry when a route resolves it: a `ResolvedReference` carries its `title` and `permalink` (`f:jxgm4i`, `f:nibxrd`).
- **Pointing, not copying.** A reference points at another entry that the site's template renders as a link (`f:i2k4jp`); a fragment's body is spliced into the entry that includes it (`f:880bg6`). The reuse page draws this line from the copying side; this page draws it from pointing.
- **Why a field and not a `cairn:` token.** A `cairn:` token in frontmatter is never rewritten and fails nothing (`f:aulk5e`), while a reference hands the template the target's title and permalink as data, which a byline or a related list needs (`f:jxgm4i`, `f:wyrefs`).
- **Who owns what.** The engine owns everything between the declaration and the rendered link: the picker (`f:bbovmp`, `f:3zswxq`, `f:i2k4jp`), the edge the manifest records (`f:5fs5o7`, `f:9i99mg`), the resolution (`f:nibxrd`, `f:mpdshq`), and the checks (`f:6ggh4v`, `f:vrfbld`, `f:2zl9zw`, `f:re5qlm`, `f:bz5j8f`). The site owns the field declaration in its adapter and the template that renders the link, and on the tutorial's site the resolve call in its entry route (`f:wyrefs`, `f:q07rd5`).
- **Where SvelteKit fits.** The resolve runs in the public entry route's server `load`, and its result reaches a Svelte component as page data (`f:wyrefs`). The admin's picker is the engine's own component, which the site does not write (`f:bbovmp`).
- **Where GitHub fits.** The id lives in the entry's markdown file in the repository. A save commits to the entry's `cairn/<concept>/<id>` branch, and a publish copies it onto the default branch, which starts the deploy (`f:cjonmm`); that deploy's build runs `verifyReferences` (`f:vrfbld`). A reference held in an unpublished draft sits on an open edit branch, so the delete guard reads a cross-branch index, fails closed when it cannot build one, and counts the draft's reference (`f:2zl9zw`, `f:7s52oz`, `f:8on7h4`).
- **Cloudflare is left out on purpose.** References keep no state in D1 or R2: entries and both manifests are committed files in git, D1 holds auth and operational rows, and R2 holds media bytes (`f:pgy0mr`). The reference check runs inside the site's Vite build (`f:vrfbld`, `f:5uhx5o`). The introduction names no Cloudflare piece, and the verification's "after the deploy" needs no host.
- **Why the checks exist.** A stored id can outlive its target. A reference has no fallback when its page renders, unlike a `cairn:` link, so the build's check is the only integrity check it gets (`f:l32sb1`, `f:6ggh4v`), and that is why `resolveReferences` drops an unresolved id instead of throwing (`f:mpdshq`). The admin catches a strand before the build: a delete refuses while any entry references the target (`f:2g0v8u`), and a rename refuses for another branch's inbound reference and otherwise rewrites each stored id in place (`f:re5qlm`, `f:gk88bv`). A save only warns (`f:bz5j8f`); the body states that, and the introduction does not.
- **"The target entry's id", not "permanent id".** An entry's id is its filename stem, and a rename moves the file to a new id and rewrites every stored reference to it (`f:46edxb`, `f:z4j689`, `f:gk88bv`). The engine's doc comments and `f:563h9u` call that id "permanent"; the page leaves the word out (friction filed).
- **The two sites.** The adapter is `src/theme/cairn.config.ts` on a scaffolded site and `src/lib/cairn.config.ts` on the add-cairn tutorial's site, and every mention of the adapter says which site it means (`f:q07rd5`). The scaffold wires the example end to end (`f:wyrefs`).
