## docs/extend/announce-on-publish.md

- `buildNewlyPublished(before, after)` returns entries where `draft` is false, `publishedAt` is set, and no prior entry at the same `concept`/`id` key carried a stamp. Source: `src/lib/delivery/manifest.ts:56-65` (`buildNewlyPublished`: `if (e.draft) return false; if (!e.publishedAt) return false; return !priorStamps.get(keyOf(e));`). [verified]
- The draft check runs before the stamp check, so a currently-unpublished entry never matches even if it carries a stamp forward from an earlier publish. Source: `src/lib/delivery/manifest.ts:61-63` (order of the two `if` guards). [verified]
- `before: null` means no prior manifest, and `buildNewlyPublished` treats every stamped, non-draft entry in `after` as newly published (a full fan-out), matching the code comment: "A null `before` indexes to nothing... every currently-live stamped entry in `after` reads as newly published." Source: `src/lib/delivery/manifest.ts:57-59` (comment plus `priorStamps` built from `before?.entries ?? []`). [verified]
- `buildNewlyPublished` is pure: no I/O, no clock read, deterministic given both manifests. Source: `src/lib/delivery/manifest.ts:56-65` (function body reads only its two arguments, no side effects). [verified]
- The entry identity key is `concept`/`id` together (`keyOf(e) = \`${e.concept}/${e.id}\``); renaming an entry changes that key, so a rename reads as a new publish since the old key's row disappears and the new key has no stamped counterpart. Source: `src/lib/delivery/manifest.ts:36` (`keyOf`). [verified]
- Deleting a published entry and recreating one under the same id also reads as a new publish, since the deleted row (stamp included) drops out of the prior manifest with no successor to carry the stamp forward. Source: derived directly from the `keyOf`/`priorStamps` logic above (no special-case for delete-then-recreate); logical consequence, not a distinct code path. [candidate: sourced to the page only, not traced to code]
- The engine sends nothing over the network on its own for publish announcements; persisting the prior manifest across deploys (KV, R2, or other storage) is the site's own responsibility. Source: page text (scope statement); consistent with `buildNewlyPublished`'s pure, no-I/O signature above. [candidate: sourced to the page only, not traced to code]

## docs/extend/auth-channel-security-model.md

- The governing rule: no control keyed on the victim's identity may deny, delay, or destroy anything; denial keys only on the requester, and an identity-keyed control either escalates through a site-actionable channel or only logs. Source: `src/lib/auth-channel/factory.ts:10` (module comment: "identity-keyed control either escalates through `challenge-required` or only logs"), instantiated by the eviction, ceiling, and escalation facts below. [verified]
- Escalation carries the wire result `challenge-required`, returned without a hard failure; a failed challenge on an already-escalated action returns `challenge-required` again, never a hard error. Source: `src/lib/auth-channel/factory.ts:62` ("`challenge-required` is a retry invitation, never a hard failure"), `:702`, `:976` (both `return { outcome: 'challenge-required' }`). [verified]
- Anything that evicts stored rows keys eviction on the requester's own bucket, so a caller can only crowd out its own pending rows, never another person's. Source: `src/lib/auth-channel/store.ts:232-239` (comment: "Filtered on `requester_bucket`, never `identity`, so an evictor..."; `WHERE requester_bucket = ?1`). [verified]
- The anti-abuse spend ceiling does not deny; crossing it logs at error to alert the site operator rather than refusing a real member's login. Source: `src/lib/auth-channel/factory.ts:337` ("logs `auth.channel.ceiling_exceeded` only, never denies"), `:779` (`log.error('auth.channel.ceiling_exceeded', ...)`). [verified]
- Every action (`request`, `confirm`, `logout`) asserts the request's `Origin` matches the site's own origin and that the connection is `https`, except on a local development host, before any code, budget, or session logic runs; both checks throw a plain 403 with no wire result. Source: `src/lib/auth-channel/factory.ts:70-78` (`assertOriginAndScheme`: `@throws HttpError 403 on an origin mismatch, or on plain http anywhere but a local host`), called at `:689` ahead of the rest of `request`. [verified]
- Identity correlates via a salted, prefixed hash: `hashToken(salt + 's:' + subject)` when a roster lookup resolved a stable subject, or `hashToken(salt + 'c:' + contact)` otherwise; logs correlate on the first 16 hex characters of this hash (`correlationId`), never on the raw contact. Source: `src/lib/auth-channel/identity.ts:6-14` (`deriveIdentity`), `src/lib/auth-channel/factory.ts:742` (`correlationId = identity.slice(0, 16)`). [verified]
- A numeric confirmation code is drawn through rejection sampling over a Web Crypto random byte range, not naive modulo, to avoid the low-end bias a non-power-of-range naive modulo introduces. Source: `src/lib/auth-channel/identity.ts:16-34` (`drawBelow`: draws bytes via `crypto.getRandomValues`, rejects draws at or above the largest multiple of the range that fits). [verified]
- A confirmed code mints a channel session resolved the same hashed-lookup way the built-in admin session is; `revokeSessions` lets site code end every session for one identity at once (roster removal, reported compromise), the one deliberate identity-keyed destructive capability since it is invoked by the site's own trusted code, not a public caller. Source: `src/lib/auth-channel/factory.ts:388,1163` (`revokeSessions(db, subject)`). [verified]
- A dev transport that prints a channel's code to console instead of sending it creates a roster oracle by construction: an unauthenticated caller can learn whether an arbitrary contact is on the roster with no code-guessing, since delivery only ever runs for a known subject; the same transport also lands plaintext one-time codes in Workers Logs if run in a deployed Worker with observability on. Source: `src/lib/auth-channel/factory.ts:867-868` (comment: "Step 8: deliver, only for a known subject"), `:855-864` (the `subject === null` branch returns without calling `config.deliver`).
