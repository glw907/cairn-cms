# Polish-11a plan review, executor and plannability lens

Adversarial read of `docs/superpowers/plans/2026-09-08-polish-11a-pass.md` (uncommitted) and its
workflow args at `~/.cache/cairn-polish-11a/11a-args.json`, against what the chain actually hands
each agent: `~/.claude/workflows/pass-execute-chains.js` gives the implementer the repo path, the
plan path, an order to read Global constraints plus Ruled inputs plus its own Task section, the
condensed `criteria`, the `files` list, the `notes`, and the gate string; it gives `diff-reviewer`
the same plan pointer, the condensed criteria, the gate string, and the implementer's JSON report.
A task is `accepted` only when the reviewer returns `accept` AND `review.gate === "pass"`; anything
else halts the single chain and defers every later task.

Seventeen findings. Ranked by what stops the run first.

`~/Projects/cairn-scratch/2026-08-16-capture/ptycapture.py`, beside `drive.py` (the prompt-matched
clack driver), `capture.sh` (whose modes are exactly `doctor-bare <site-dir>` and

specifies. The plan's method is "scaffold a fresh site into a scratch directory", and the recorded

## Gate proposal

The spec forecloses dropping checks. `2026-09-08-polish-passes-design.md:559-570` says each plan
re-derives the gate from `.github/workflows/` and records it, with `npm run check` 0/0 and
`npm test` exit 0 as the floor, `check:rulings-format` named explicitly, and "the CLI suite and
`check:template` run per task, because a file move can carry pinned text"; the initiative design's
standing constraint at `:137-139` defines the full gate the same way. So no check in the string may
be removed for cost, and the e2e is inside the derived list because `e2e.yml` is one of the derived
workflows. That is the ruling; the proposal below therefore does not drop a check.

What the string does do is build the package thirteen times per run. Measured from
`package.json`: `npm run package` is `svelte-package` plus the admin-CSS build plus the dist-Svelte
transpile, and it is chained as a prerequisite inside `check:package`, `check:reference`,
`check:reference:signatures`, `check:surface`, `check:self-use`, `check:readiness`, `check:visuals`,
`check:snippets`, `check:custom-surface`, `check:invisible-craft`, `check:admin-css-classes`, and
`check:consumers`, twelve times, plus the standalone `npm run package` the string already runs
first. At a conservative 40 to 60 seconds per build that is 9 to 13 minutes per gate run spent
rebuilding an unchanged `dist`. Around it sit `svelte-check` over the library, a vitest run over 447
test files across four projects, the showcase's own check and unit runs, Vale, ESLint, the CLI
suite, and a Playwright run over 33 spec files behind a preview build. Estimate: 25 to 40 minutes
per gate run, and the pass runs it about nineteen times (twelve tasks, two of which gate twice per
their own two-commit structure, plus the fix rounds `maxFix: 1` allows and the pass-end ritual), so
roughly 8 to 12 hours of gate wall clock, of which 2.5 to 4 hours is the repeated packaging alone.

Proposal, coverage-identical and spec-compliant: run `npm run package` ONCE at the head of the gate
string and invoke the twelve dependent checks as their underlying `node scripts/checks/*.mjs`
commands rather than through the npm scripts that re-chain the build. Every check still runs, in the
same order, against the same artifact. This is a wrapper change, not a list change, so the derived
list the spec mandates is untouched. Cut the string once in the plan's Gate section, put it in the
args verbatim (the two are byte-identical today, which is the one fidelity item that is fully
clean), and keep the current npm-script form as the pass-end and pre-merge run so the wrappers
themselves are proven at least once.

If more is wanted, the only remaining candidate is the per-task e2e, and it needs Geoff's ruling
rather than a plan edit, because the spec's derived-list rule covers it. The argument for asking:
the plan already leaves `design.yml`'s styleguide e2e to CI on the reasoning that a browser matrix
is what a per-task local loop cannot afford (Plan:1061-1066), and eight of the twelve tasks touch
no route behavior at all (Tasks 7, 9, 10, 11, 12 provably, and 1, 2, 4 are pure moves the unit
suites cover). Reserving the e2e for the checkpoints (Tasks 3, 6, 9, 12) plus every task that
touches a `.svelte` file would save roughly half the remaining gate time. Do not take that
reduction inside the pass without the ruling.
