# Agent-drafted docs: writer guidance, audience evaluation, and where each role lives

Research date 2026-09-23. Every claim carries its source. **[Inference]** marks my own reasoning where no source says it directly.

## 1. Getting Claude to write documentation well

- **A role helps, but only a little.** Anthropic says a role in the system prompt "focuses Claude's behavior and tone," and that even one sentence helps. The guide gives examples a stronger endorsement: "one of the most reliable ways to steer Claude's output format, tone, and structure," with 3 to 5 relevant, diverse examples wrapped in `<example>` tags. It also recommends stating the motivation behind each instruction. ([prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices))
- **Pick canonical examples, not rule lists.** Context engineering means "the smallest set of high-signal tokens" at the "right altitude." Anthropic recommends "diverse, canonical examples" over a long list of edge cases. ([Effective context engineering, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents))
- **Give the writer a check it can run.** Claude Code's top practice is "Give Claude a check it can run." Without one, "'looks done' is the only signal available." Anthropic also recommends a Writer/Reviewer split, because "a fresh context improves code review," and warns that a reviewer asked to find gaps "will usually report some" even when the work is sound. ([Claude Code best practices](https://code.claude.com/docs/en/best-practices))
- **Describe to a new hire, then test against real tasks.** For tool descriptions, which are docs whose reader is an agent, Anthropic says to describe the tool as "to a new hire" and make implicit context explicit. It then evaluates on realistic multi-step tasks with verifiable outcomes and held-out sets. ([Writing tools for agents, 2025-09-11](https://www.anthropic.com/engineering/writing-tools-for-agents)) "Building effective agents" adds: "put yourself in the model's shoes" and "test how the model uses your tools." ([2024-12-19](https://www.anthropic.com/engineering/building-effective-agents))
- **Anthropic's own document skill tests with a reader.** Its `doc-coauthoring` skill has a Reader Testing stage. A fresh Claude with "no context bleed" answers 5 to 10 predicted reader questions, which "catches blind spots." ([anthropics/skills doc-coauthoring](https://raw.githubusercontent.com/anthropics/skills/main/skills/doc-coauthoring/SKILL.md)) This is the closest Anthropic comes to explicit guidance on writing docs.
- **Build the eval before the content.** The skill-authoring guide says "Create evaluations BEFORE writing extensive documentation." It runs the Claude A/Claude B loop: one instance authors, a fresh instance does real tasks, and you watch where it struggles. It also assumes "Claude is already very smart," so the writer adds only what Claude lacks. ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices))
- **Human-written context helps agents, but only slightly.** Context files gave agents little net benefit. LLM-generated files cut success about 3%. Human-written files raised it about 4%. Both raised cost by more than 20%. Agents followed *instructions* but gained nothing from *repository overviews*. ([Gloaguen et al., arXiv 2602.11988, rev. 2026-06](https://arxiv.org/abs/2602.11988))

## 2. Evaluating drafts from an audience's perspective

- **Expert personas don't raise accuracy.** Across six models on GPQA and MMLU-Pro, expert personas had no significant effect. Low-knowledge personas often *lowered* accuracy. The authors recommend task-specific instructions instead. ([Basil, Mollick et al., arXiv 2512.05858, 2025-12](https://arxiv.org/abs/2512.05858))
- **A persona prompt can't make the model forget what it knows.** Told to "act like a 5th grader," models scored 0.96 to 0.99 against real students' 0.687. What closed the gap was structural: remove the source text from context so the model can't use it. ([arXiv 2608.30033, 2026-08-30](https://arxiv.org/html/2608.30033)) **[Inference]** A grader told to read "as a non-technical editor" still reads with expert knowledge. It can't reliably flag what that reader wouldn't understand.
- **LLM judges miss most real defects.** A production judge caught about 18% of defect patterns. On one batch it passed 100 rounds that humans found had 23 defects. Half the missed patterns fell in dimensions the rubric had no category for. ([arXiv 2606.10315](https://arxiv.org/html/2606.10315v1))
- **Judges check what's present, not what's missing.** Recall improves with explicit omission audits, a reference to compare against, and checklists. ([arXiv 2608.31016](https://arxiv.org/pdf/2608.31016)) This matches the local finding: fluent graders passed pages that failed when an agent actually used them.
- **Simulated users aren't perfect proxies either.** Success rates varied by up to 9 points depending on which LLM played the user. Simulators were too cooperative and miscalibrated by task difficulty. ([Lost in Simulation, arXiv 2601.17087, 2026-01](https://arxiv.org/abs/2601.17087)) This cuts against over-trusting reader agents as stand-ins for *humans*. It matters less when the reader really is an agent.
- **Anthropic's eval guidance.** It names three grader types. Code-based graders are fast and objective but brittle. Model-based graders are nuanced but "require calibration with human graders." Human graders are the gold standard but expensive. Anthropic says to "grade what the agent produced, not the path," to read transcripts, and to separate capability evals (low pass rate) from regression evals (near 100%). ([Demystifying evals, 2026-01-09](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)) Its platform docs rank code-based grading fastest and most reliable. They say to prefer volume over polish, to use detailed rubrics with explicit reasoning, and to grade with a different model. ([Define success criteria and build evaluations](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests))

## 3. Practitioner experience testing docs with agents

- **Mintlify ran agents against docs sites.** In 2,400 agent runs across 20 docs sites, one llms.txt link cut 404s by about 90%. But "the map didn't make them more right, it just got them there faster." ([Mintlify, 2026-07-17](https://www.mintlify.com/blog/llms-txt-agent-benchmark)) Fern and Mintlify publish agent-readiness scores. These are static checks, not task runs. ([Fern Agent Score](https://buildwithfern.com/agent-score/company/mintlify-com-docs))
- **Vercel tested docs delivery by task outcome.** It ran hardened evals with behavior-based assertions. A compressed 8KB docs index in AGENTS.md passed 100%. Skills passed 53%, or 79% when told to use them. In 56% of cases the skill was never invoked. ([Vercel, 2026-01-27](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals))
- **Stripe grades deterministically.** Its integration benchmark checks results against real Stripe objects, not an LLM judgment, and names validation, not generation, as the core limit. ([InfoQ, 2026-07-15](https://www.infoq.com/news/2026/07/stripe-ai-agents-benchmark/); [Stripe post](https://stripe.com/blog/can-ai-agents-build-real-stripe-integrations))
- **A practitioner case study.** Seven independent reader agents answered structured task questions, such as "find the most important command in 15 seconds." All seven converged on the same five defects, including missing auth steps and missing error handling. Fresh validator agents then checked the fixes. ([Petrenko, 2026-01-24](https://jonnyzzz.com/blog/2026/01/24/16-ai-agents-documentation-refactor/)) This is a single anecdote, not a controlled study.
- **Docs as Tests.** Doc Detective executes the steps a doc describes (CLI, API, UI), so the docs double as product tests. It now ships agent skills. ([Doc Detective](https://doc-detective.com/docs/get-started/tests); [agent-tools](https://github.com/doc-detective/agent-tools); [docsastests.com](https://www.docsastests.com/))

## 4. Skill, subagent, or both

- **Subagents enforce tool limits and isolate context.** They're recommended when "you want to enforce specific tool restrictions or permissions" and the work is self-contained. `tools` and `disallowedTools` set the ceiling. Each subagent starts with "a fresh, isolated context window." ([Subagents docs](https://code.claude.com/docs/en/sub-agents))
- **The two combine.** A subagent's `skills` field preloads full skill content at startup. A skill with `context: fork` plus `agent:` runs its body as the task inside a chosen agent type. ([Subagents](https://code.claude.com/docs/en/sub-agents); [Skills](https://code.claude.com/docs/en/skills))
- **Skills load on demand, which can fail.** A skill loads only when invoked. Vercel's data shows agents often skip optional retrieval. ([Skills](https://code.claude.com/docs/en/skills); [Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)) **[Inference]** So the writer should always get the audience profile through an explicit load: a preloaded `skills:` entry or a dispatch-prompt include. Never leave it to discretionary invocation.
- **Where each role lives:** (i) Writer-side audience knowledge goes in a skill: a short profile plus canonical exemplars, preloaded into the drafter. (ii) The reader or tester role goes in a subagent definition whose `tools` field enforces the reader's ceiling. The arrival state and the job come in the dispatch prompt. This is the pairing the docs describe. **[Inference]** A tool allowlist is only a partial ceiling. A reader agent limited to dashboards and a CLI still knows SvelteKit. Also cap what it knows by withholding repo and source access and giving it only the docs.

## Implications for method (a) vs (b)

**Recommendation: adopt (b), and keep one narrow piece of (a).** Every strand of the evidence points the same way:

- Anthropic's guidance favors checks that run over judgments.
- Persona prompts don't change what a model knows.
- LLM judges systematically miss omissions and anything outside their rubric.
- Practitioners who got real signal (Vercel, Stripe, Mintlify, Petrenko) graded on task outcomes.

Your 15-defects result matches the published pattern. It isn't an outlier.

**Keep from (a):** a *short* profile file as writer context, delivered as a preloaded skill with 2 to 3 canonical exemplar pages. Use an LLM grader only for register and tone, where no checkable outcome exists. Give it an explicit omission checklist.

**Cautions against (b) as stated:**

1. Reader agents are poor proxies for the two human-only audiences, evaluators and non-technical editors. Simulators are too cooperative and too knowledgeable. For those audiences, bound knowledge structurally: give the reader only the page, no repo, and ask it to list every term or step it had to assume. Treat the result as a floor, not a verdict. Occasional human checks remain the gold standard for those audiences.
2. Grade outcomes in code wherever possible, with Doc Detective-style literal execution for procedures. A reader agent's self-report of "done" is itself a judgment and needs a deterministic check behind it.
3. Separate capability jobs from regression jobs, and run each job several times (pass^k). Watch cost: each reader run is expensive, and context files alone added 20% or more per task in the AGENTS.md study.

**A possible third option:** make docs-as-tests the base layer. Executable procedure blocks run literally for operator and extender jobs. Reserve reader agents for comprehension-and-judgment jobs that no script can check.

**Where evidence is thin:** No published study compares persona-rubric grading against task-completion testing *for documentation*. The judge and persona findings come from other domains: QA, clinical notes, commerce agents, tutoring. Anthropic publishes no docs-writing guidance beyond the doc-coauthoring skill and the tool-description advice. The practitioner reports are vendor blogs or single cases.
