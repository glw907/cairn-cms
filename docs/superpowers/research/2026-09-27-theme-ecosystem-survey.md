# Theme ecosystem survey (2026-09-27)

Neutral survey dispatched during the theme identity pass B brainstorm, before the spec existed. Input to the spec review's theme-ecosystems lens.

## Theme-system research report

### WordPress block themes / theme.json
1. **Contract**: `theme.json` (settings + styles) plus `style.css` header; no required templates since block themes can inherit core block markup. Settings define what's editable (palette, type scale, spacing); Styles apply defaults. [Global Settings & Styles handbook](https://developer.wordpress.org/block-editor/how-to-guides/themes/global-settings-and-styles/). Validation for the official directory runs through the Theme Review Team's published requirements and Theme Unit Test data, not an automated schema linter alone — human review plus automated sniffs [Theme Review Guidelines](https://developer.wordpress.org/themes/releasing-your-theme/theme-review-guidelines/), [Theme Review Requirements](https://make.wordpress.org/themes/2015/05/27/theme-review-requirements-and-documentation/).
2. **Divergence**: tokens-only (`appearanceTools: true` turns on the full token surface) up to full block markup and per-block style overrides; **style variations** (JSON files under `/styles`) let one theme ship several distinct looks without separate themes or child themes [CSS-Tricks on style variations](https://css-tricks.com/creating-style-variations-in-wordpress-block-themes/). A block child theme needs only a folder with `theme.json` + `style.css`, auto-registered [Kinsta on child themes](https://kinsta.com/blog/customize-block-in-child-theme/).
3. **New component theming**: a block reads global settings/styles through the same token system; WordPress 6.6+ lets themes define custom CSS variables directly in `theme.json`, and version 3 adds enhanced style inheritance [WPVIP on theme.json](https://wpvip.com/blog/using-a-design-system-with-the-wordpress-block-editor-pt-1-theme-json/).
4. **Upgrades**: theme.json is versioned (schema `$schema`/version number); a theme opts into new settings by bumping the version, old themes keep old defaults — an inherited-contract model, not copy-paste. WP 6.6 added export/import of Global Styles customizations so non-developers can carry token edits across theme changes [WPVIP](https://wpvip.com/blog/using-a-design-system-with-the-wordpress-block-editor-pt-1-theme-json/).
5. **Praise/complaints**: praised for genuinely swappable full-site tokens and style variations reducing the need for child themes; documented friction is the size and evolving nature of the settings schema across theme.json versions (1/2/3), which developers must track [10up reference](https://gutenberg.10up.com/reference/Themes/theme-json/).

### Ghost themes (Handlebars)
1. **Contract**: Handlebars templates plus required helpers (`{{ghost_head}}`, `{{ghost_foot}}`, etc.) and a `package.json` with `config.custom` for site-owner settings. Validated by **gscan**, a rules engine where each rule has a pass/fail check and fix guidance, distinguishing errors (must fix) from warnings (deprecated features) [gscan README](https://github.com/TryGhost/gscan/blob/main/README.md), [Ghost theme docs](https://docs.ghost.org/themes).
2. **Divergence**: full template control — Handlebars gives complete markup freedom; only the required helpers are non-negotiable.
3. **New component theming**: a new Ghost feature (custom fields, new post type element) typically requires new Handlebars helpers; because gscan validates against a known helper set, **custom helpers registered by an app can fail gscan validation**, a documented rough edge for extending themes beyond the built-in vocabulary [gscan issue #86](https://github.com/TryGhost/gscan/issues/86).
4. **Upgrades**: versioned compatibility — gscan targets "current and last major" Ghost versions, so a theme is checked against a moving target each major bump, not automatically inherited [gscan.ghost.org](https://gscan.ghost.org/).
5. **Praise/complaints**: gscan is praised as a fast, actionable pre-submission check; the complaint thread is specifically about the custom-helper validation gap blocking legitimate app-driven extension [gscan issue #86](https://github.com/TryGhost/gscan/issues/86).

### Shopify Online Store 2.0 / Dawn
1. **Contract**: `settings_schema.json` (global theme settings), sections/blocks JSON templates, `theme.liquid` with required `{{ content_for_* }}` hooks. Validated by **Theme Check**, a static linter for Liquid/JSON catching syntax errors, missing snippets, deprecated tags/filters, and Core Web Vitals issues (asset size, missing `width`/`height`, render-blocking scripts) [Theme Check docs](https://shopify.dev/docs/storefronts/themes/tools/theme-check/index), [Theme Check GitHub](https://github.com/Shopify/theme-check). Theme Store submission requires **Theme Store requirements** beyond Theme Check, including "Sections Everywhere" and per-element blocks on product pages [Theme store requirements](https://shopify.dev/docs/storefronts/themes/store/requirements).
2. **Divergence**: full template/section freedom; Dawn is a reference theme, not a base class — a submitted theme must be "substantively different" from Dawn/Horizon, explicitly barring derivative submissions [Dawn README](https://github.com/Shopify/dawn), [Theme store requirements](https://shopify.dev/docs/storefronts/themes/store/requirements).
3. **New component theming**: sections/blocks are the extension unit — a merchant-facing feature ships as a new section type with its own schema, composable into any theme that supports "sections everywhere"; this is the mechanism, not shared tokens per se.
4. **Upgrades**: copy-and-diverge — Dawn is a starting point copied into a new theme, then the two repos diverge; Shopify's own "Updating themes" help page documents manual merge/update as the reality for theme owners [Updating themes](https://help.shopify.com/en/manual/online-store/themes/managing-themes/updating-themes).
5. **Praise/complaints**: praised for standardizing extensibility (any block anywhere) and CWV enforcement baked into the linter; friction is that the linted Liquid and the Liquid Shopify actually runs can diverge, a known gap developers flag ["The Liquid you lint isn't the Liquid Shopify runs"](https://dev.to/iamrobindhiman/the-liquid-you-lint-isnt-the-liquid-shopify-runs-5bhp).

### Hugo themes
1. **Contract**: minimal — a theme is a set of layouts/static/archetypes files; no required manifest beyond `theme.toml`/module config for discovery.
2. **Divergence**: full template control, file-level override via lookup order.
3. **New component theming**: no shared token layer by default — a new partial in a project's `layouts/` simply wins over the theme's by Hugo's most-specific-file-wins **lookup order**, which interleaves project and theme directories and merges at file granularity, left-most (highest-priority) component wins for multi-component setups [Template lookup order](https://gohugo.io/templates/lookup-order/), [Theme components](https://gohugo.io/hugo-modules/theme-components/).
4. **Upgrades**: theme updates are a separate git/module dependency; overrides are copy-and-diverge at the file level, but only for the specific overridden file, so most of the theme still updates cleanly — a partial-inheritance model.
5. **Praise/complaints**: praised for its precision (override exactly the file you need, nothing else) and predictability of the lookup order; no strong documented complaint surfaced in this pass beyond the general small-ecosystem tradeoffs of file-based override (no schema, no linter).

### Astro Starlight
1. **Contract**: no required files for basic use; theming is CSS custom properties (`--sl-color-*` etc.) plus an optional `components` map in Starlight's config for full component replacement [CSS & Styling](https://starlight.astro.build/guides/css-and-tailwind/), [Overrides Reference](https://starlight.astro.build/reference/overrides/).
2. **Divergence**: two tiers — token-only recoloring (override CSS variables), or complete component replacement per named slot, with an interactive "Overrides Map" documenting every replaceable component [Overriding Components](https://starlight.astro.build/guides/overriding-components/).
3. **New component theming**: an override component receives the global `starlightRoute` object so it can render consistently with the rest of the page; new/overridden components read the same CSS variables as the defaults, so they inherit theming automatically unless replaced outright.
4. **Upgrades**: inherited-by-default — only explicitly named overrides diverge from Starlight's shipped component; everything else tracks upstream automatically, closest to an "inherited defaults" model among the systems studied.
5. **Praise/complaints**: praised for exposing the "entire visual design" through variables and for granular, named override points rather than an all-or-nothing template fork [CSS & Styling](https://starlight.astro.build/guides/css-and-tailwind/).

### Gatsby themes (component shadowing) — struggled
1. **Contract**: a theme was an npm package (a Gatsby plugin) whose files under `src/` could be "shadowed" by placing a same-path file in the consuming site.
2. **Divergence**: full-file replacement at match precision.
3. **New component/theming problem**: shadowing broke down exactly at composition — scoped npm packages could not be shadowed at all, and with **multiple ancestor themes, shadowing only resolved the first match**, not a proper override chain [Gatsby shadowing issue #11951](https://github.com/gatsbyjs/gatsby/issues/11951), [scoped-package issue #14134](https://github.com/gatsbyjs/gatsby/issues/14134). Gatsby's own team broadened shadowing from `src/components` to all of `src/` because "people had trouble remembering which folders got shadowed" — a discoverability failure in the core mechanic [Themes Update blog](https://www.gatsbyjs.com/blog/2019-01-29-themes-update-child-theming-and-component-shadowing/).
4. **Upgrades**: shadow files silently diverge from the theme file they shadow, with no notification on upstream changes — pure copy-and-forget once shadowed, worsened by monorepo/webpack symlink resolution breaking after a major Gatsby version bump [issue #30335](https://github.com/gatsbyjs/gatsby/issues/30335).
5. **Complaints**: composition (multiple themes), package scoping, and monorepo symlink handling were all separately broken, indicating the mechanism was under-specified for real multi-theme stacks.

### Drupal theming — struggled, then re-architected
1. **Contract (old model)**: base themes (e.g., Classy) subthemed via inheritance; a subtheme inherited templates/preprocess functions and overrode by copying specific `.html.twig` files.
2. **Divergence**: full override via copied Twig templates, but **inheritance was the problem**: Classy stopped receiving updates after Drupal 8.0.0 specifically because any change risked breaking every subtheme depending on its exact markup — the base theme became frozen by its own downstream contract [Starterkit blog](https://www.drupal.org/about/core/blog/new-starterkit-will-change-how-you-create-themes-in-drupal-10).
3. **New component theming**: under the old model, a new core feature's markup had to be added to the base theme, which then risked "regressions" in every subtheme that had already diverged — the inheritance chain made upstream evolution costly [Starterkit blog](https://www.drupal.org/about/core/blog/new-starterkit-will-change-how-you-create-themes-in-drupal-10).
4. **Upgrades (fix)**: Drupal 10 replaced inheritance with **Starterkit**, a generator that *copies* a clean starting template into a new theme rather than subclassing a base theme — explicitly because "most custom themes are based on bespoke designs that aren't a good fit for subtheming an opinionated theme" [Starterkit blog](https://www.drupal.org/about/core/blog/new-starterkit-will-change-how-you-create-themes-in-drupal-10), [Specbee explainer](https://www.specbee.com/blogs/starterkit-theme-in-drupal-10). This traded "inherited defaults" for "copy-and-fork," a deliberate concession that inheritance had failed in practice for divergent designs.
5. **Complaints**: the core admission is notable — Drupal's own core blog states base-theme inheritance couldn't evolve without breaking bespoke subthemes, so the team moved to the opposite model (copy-on-create) rather than trying to fix inheritance.

### Jekyll gem-based themes — struggled
1. **Contract**: a theme is a Ruby gem containing `_layouts`, `_includes`, `_sass`, etc.
2. **Divergence**: full override, but files live inside the installed gem, invisible in the project tree [Jekyll Themes docs](https://jekyllrb.com/docs/themes/).
3. **New component theming**: no shared token layer; overriding means manually locating the gem via `bundle show <theme>` and copying the specific file into the project, a multi-step, low-discoverability workflow [Themes docs](https://jekyllrb.com/docs/themes/); Minimal Mistakes' own docs devote a full "Overriding Theme Defaults" page to this exact friction [Minimal Mistakes docs](https://mmistakes.github.io/minimal-mistakes/docs/overriding-theme-defaults/).
4. **Upgrades**: once a file is copied out of the gem into the project, it silently diverges from future gem updates — copy-and-forget, same failure mode as Gatsby shadowing but manual rather than automatic.
5. **Complaints**: GitHub Pages' forced default theme (`jekyll-theme-primer`) with no override path was raised as a separate, blocking pain point in Jekyll's own issue tracker [issue #7047](https://github.com/jekyll/jekyll/issues/7047).

### Component-library angle: token systems
- **daisyUI**: semantic tokens (`primary`, `secondary`, `accent`, `neutral`, etc.) as CSS variables per `data-theme`; a full re-theme is "a few lines of CSS variables," and multiple themes can coexist and be switched at runtime without per-element classes [daisyUI themes docs](https://daisyui.com/docs/themes/), [Alberto Duran on DaisyUI 5 theming](https://albertoduran.com/thejournal/building_albertoduran/design/daisy_theming/). Praised specifically because semantic naming means authors don't hand-write dark-mode variants per element.
- **shadcn/ui**: explicitly "not a component library, it is how you build your component library" — components are copied into the consumer's own codebase, and theming is one file (`globals.css`) of CSS variables consumed by every component; adding a theme touches no component code [Theming docs](https://ui.shadcn.com/docs/theming). The tradeoff (not asked for here but load-bearing): because components are copied, not versioned-and-inherited, upstream shadcn fixes don't reach a project automatically — the same copy-and-fork tradeoff as Drupal's Starterkit and Jekyll gems, chosen deliberately for full code ownership.
- **Material Design 3**: token system is deep — color roles, surface containers, shape, density, and motion tokens, generated from seed colors via the HCT algorithm, composed through a Sass theming API; Google ships the Material Theme Builder (Figma plugin + codegen) specifically because hand-authoring the full token set is nontrivial [M3 Customization](https://m3.material.io/foundations/customization), [Theme Builder](https://m3.material.io/blog/material-theme-builder). This is the "over-specified" end: powerful and systematic, but requiring tooling to be practical.
- **W3C Design Tokens Community Group (DTCG)**: a vendor-neutral JSON format for token interchange, reaching its first stable spec (2025.10) precisely because token formats had fragmented across tools, causing "drift, errors, and maintenance overhead" for teams running multi-brand systems [DTCG spec announcement](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/), [Design Tokens Format Module](https://www.designtokens.org/tr/drafts/format/).

## Synthesis: 8–12 testable lessons

1. **Defaults inherited, not copied, let upgrades reach existing themes automatically.** Positive: Astro Starlight (unnamed components silently track upstream; CSS & Styling docs), WordPress theme.json (versioned schema, Global Styles export/import). Negative: Gatsby shadowing and Jekyll gem themes both copy-on-override with no forward propagation; Drupal's Classy base theme froze because inheritance couldn't evolve without breaking subthemes, forcing a move to copy-on-create (Starterkit) as the deliberate alternative.

2. **A narrow, named override surface beats an implicit file-path convention.** Positive: Starlight's explicit `components` map plus a documented Overrides Map. Negative: Gatsby shadowing's implicit path-matching caused "people had trouble remembering which folders got shadowed," prompting a scope change, and still failed silently across scoped packages and multi-theme ancestry.

3. **Composition (more than one theme/plugin contributing overrides) is where override mechanisms break first, and must be designed in, not discovered.** Negative evidence only: Gatsby shadowing resolved just the first ancestor when multiple themes shadowed the same file (issue #11951); no system reviewed here documents composition working well at the file-override tier — Hugo's lookup order (multiple theme components, project wins) is the closest positive counterexample.

4. **Automated validation (linter/scanner) catches structural drift that human review alone misses, but its rule set can itself lag the runtime, becoming a false floor.** Positive: gscan and Shopify Theme Check both give fast, itemized pass/fail feedback pre-submission. Negative: Theme Check's linted Liquid can diverge from Shopify's actual runtime Liquid; gscan rejects legitimate custom-helper extensions it doesn't recognize.

5. **A component-level extension unit (Shopify's sections/blocks) scales new capability better than a template-fork unit.** Positive: Shopify's "sections everywhere" requirement means any merchant feature composes as a block on any conforming theme without per-theme rework.

6. **Semantic (role-based) tokens reduce the *combinatorial* theming burden more than raw value tokens.** Positive: daisyUI's `primary`/`neutral`/etc. tokens eliminate hand-authored per-element dark-mode variants; shadcn/ui's single `globals.css` variable file re-themes every component. Negative counterexample by contrast: Material Design 3's much larger token surface (color roles + surface containers + shape + density + motion) needs a dedicated builder tool to author by hand — a sign the token set itself can outgrow manual authorship.

7. **A copy-based distribution model (copy-paste or generator-copy) trades update propagation for full ownership, and is a legitimate deliberate choice, not automatically inferior.** Evidence: Drupal explicitly chose copy-on-create (Starterkit) over inheritance for bespoke designs; shadcn/ui explicitly chose copy-into-project over a package dependency. Both name the same tradeoff (no free upstream fixes) as an accepted cost for design freedom.

8. **A format-interchange standard emerges only after real fragmentation pain, and its job is tool interoperability, not authoring ergonomics.** Evidence: the W3C DTCG spec exists because "teams maintaining multi-brand design systems... juggle dozens or even hundreds of token files manually, leading to drift, errors, and maintenance overhead" — a lesson that a growing theme ecosystem eventually needs a shared token *format*, separate from any one system's theming API.

9. **Discoverability of override files matters as much as the override mechanism itself.** Negative: Jekyll's gem-based theme files are invisible in the project tree, requiring `bundle show` just to locate what to override; Gatsby's shadowing had the same "which folder" confusion. Positive counterexample: Hugo and Starlight keep the override surface visible (project `layouts/`, or an explicit component map) inside the developer's own tree.

10. **Full-file-replacement escape hatches are necessary but should be the last resort, not the primary API**, because they forfeit both validation and future updates for that file. Every system studied offers one (Hugo lookup order, Starlight component override, WordPress full block/template override, Shopify duplicate-and-diverge from Dawn), but the systems judged more pleasant (WordPress style variations, Starlight CSS variables, daisyUI/shadcn tokens) push token-level theming first and treat full override as the exception.

11. **A contract can be under-specified (Gatsby: no rule for multi-theme shadowing, no scoped-package support) or over-specified (Material Design 3's full multi-axis token system needing a builder tool) — both raise the cost of building a new theme**, one through undefined behavior in real usage, the other through sheer authoring surface area; the systems praised as pleasant (Starlight, daisyUI, WordPress style variations) sit in between: a small, named, mostly-optional token set with an explicit full-override escape hatch.

12. **A validator's job is best scoped to structural/contract conformance (files present, helpers recognized, JSON valid, performance budgets), not to gatekeeping legitimate extension.** Positive: Shopify Theme Check's CWV checks (asset size thresholds, missing dimensions) catch real regressions. Negative: gscan's custom-helper rejection blocks legitimate app-added functionality, showing a validator can conflate "not in my known vocabulary" with "invalid."
